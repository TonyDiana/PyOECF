    Estrategia de programación¶

    Ámbito: Este documento define el estándar general de desarrollo TD. Es aplicable a cualquier proyecto, sea biblioteca o aplicación. Versión: 26.10

    Filosofía y principios generales (TEP-8)¶

    El proyecto se rige por principios que priorizan la claridad, la accesibilidad y la ausencia de ambigüedad. Son la base de todas las decisiones técnicas y de estilo.

    El PEP8 será respetado siempre, a menos que entre en conflicto con la capacidad de comprensión del código.

    La claridad visual no es un lujo. Para un disléxico, el código desordenado es una tortura visual y mental, es como intentar leer un libro cuyo texto se reordena solo.

    Respeta esta necesidad.

    Escritura de la codificación¶

    Idioma de codificación¶

    • El idioma fundamental de la codificación será el español.

    • JAMÁS se utilizarán tildes ni la letra ñ en ninguna variable o constante. Se utilizará el inglés para resolver cualquier conflicto.

    • Se utilizará el inglés para variables y constantes típicas de programación ya acostumbradas (next, aux, time, temp, etc...).

    • Siempre se comentará en español, jamás en inglés.

    • Si se toma parte de una biblioteca externa y se acondiciona o ajusta, la documentación y docstrings se respetarán en el idioma original. Podría añadirse una versión traducida.

    Documentación del proyecto¶

    • Se utilizan docstrings en el código fuente de forma prioritaria.

    • Los docstrings nunca acaban en punto, la documentación siempre se escribe correctamente.

    • Evitar los dobles comentarios, tienen prioridad los comentarios que sirven para documentar con MkDocs (los docstrings, que lee mkdocstrings).

    • MkDocs será el eje de la documentación del desarrollador, desplegada en formato HTML.

    • MkDocs presenta adecuadamente el texto de los .md cuyas líneas disponen de más de 80 caracteres de largo. No se perderá el tiempo arreglando las líneas en VSC ya que el editor también ayuda con este principio.

    Principios innegociables¶

    • Mejor legible que compacto.

    • Mejor comprensible que pragmático.

    • Mejor explícito que implícito.

    • Todo código o página de manual debe pasar corrector ortográfico, SIEMPRE.

    • Se usan comillas dobles en vez de comillas simples, SIEMPRE. Tengamos presente que 'A' representa el número decimal 65 en muchos lenguajes de programación; parece más universal utilizar las comillas dobles para strings, aunque la tradición pythónica es utilizar la simple. La comilla simple pasa desapercibida en muchas ocasiones para un disléxico.

    Literales mágicos¶

    Se denominan literales mágicos los valores literales dispersos en el código sin nombre ni constante que los represente. No confundir con los métodos especiales (dunder) de Python.

    • Están prohibidos, mejor usar diccionarios de constantes o clases.

    • Estarán colocados en el lugar más visible posible, normalmente al principio del código.

    • En caso de que un literal mágico se use una sola vez, se podrá utilizar para simplificar el código, pero se comentará de manera inequívoca. Ejemplo:

    Python¶

    Principios¶

    • Se denomina módulo a un archivo .py; paquete a una carpeta con __init__.py y sus módulos; biblioteca a un conjunto abstracto diseñado para ser consumido por otras aplicaciones; suite a un conjunto de bibliotecas relacionadas; y aplicación al código Python ejecutable de forma autónoma por un usuario final.

    • Los paquetes y bibliotecas siempre se denominarán en minúsculas, según se establece en el PEP8.

    • Las anotaciones de tipo son obligatorias en toda función, método y propiedad. Nunca se omitirán.

    • El # type: ignore se usará exclusivamente cuando Pylance no pueda inferir el tipo por limitaciones del análisis estático, nunca para ocultar errores reales.

    • Las variables locales de método nunca usarán __ (doble guión bajo); se usará _ como máximo.

    • Mejor pedir perdón que permiso. Las excepciones generadas serán parte aceptable en los códigos.

    __all__¶

    • Declara el contrato público del módulo: qué existe para el exterior.

    • Presentará los elementos ordenados según se declaren.

    • Cuando un módulo no deba exportar nada, se declarará explícitamente vacío:

    1
    __all__ = []

    Imports¶

    • Los imports dentro de un paquete serán siempre relativos.

    • Un módulo conoce la profundidad de sus propios hermanos, no la de los ajenos. Por tanto:

    • Dentro del paquete propio → imports relativos (., ..) según la profundidad real.

    • Hacia paquetes ajenos dentro de la misma aplicación → import desnudo (import bib, import hub), nunca relativo cruzado.

    • El entry point de la aplicación (src/__main__.py) es responsable de añadir src/ al sys.path para hacer posible este esquema.

    • Las bibliotecas independientes no pueden asumir ningún sys.path externo. Todos sus imports serán siempre relativos.

    • Ningún paquete busca nada fuera de sí mismo, salvo bibliotecas externas o el paquete hub.

    • Todo paquete expone en su __init__.py aquello que puede compartir. Lo que no se expone, no se busca desde fuera.

    • Los imports desde fuera de un paquete van siempre a su __init__, nunca al módulo interno. La forma canónica es:

    1
    from <paquete> import <modulo>
    • Excepción: se permite entrar al módulo interno de una biblioteca externa si la sintaxis resultante es clara y explícita, y evita una abreviatura que de otro modo sería necesaria. La profundidad máxima permitida son dos niveles antes del import:
    1
    from bib.net import mi_ip   # válido: claro, explícito, evita abreviatura

    • Los imports que no estén al principio del módulo, sino dentro de funciones o métodos, se colocarán junto a su uso, nunca dispersos al inicio del archivo.

    • Los nombres importados en una misma línea (from <paquete> import a, b, c) se ordenarán siempre alfabéticamente.

    Paquete hub¶

    • Todo elemento que deba ser compartido por más de un paquete de la aplicación vivirá en el paquete hub.

    • hub no busca nada fuera de su propio paquete: sin imports de paquetes hermanos, sin imports de kernel, website ni ningún otro. Esta restricción es la que elimina la posibilidad de referencias circulares.

    • El criterio de entrada es estricto: si algo lo necesita un solo paquete, se queda en ese paquete. En cuanto un segundo paquete lo necesita, se mueve a hub.

    • Las bibliotecas independientes no utilizan este patrón.

    Nomenclatura de módulos y paquetes¶

    • Los nombres de módulos y paquetes serán suficientemente descriptivos. Sin abreviaciones crípticas: el nombre debe explicarse solo.

    • Ningún módulo se llamará igual que su paquete. Si existe un módulo central que da nombre conceptual al paquete, ese módulo se llamará núcleo o kernel a elección del desarrollador.

    • Se preferirá un paquete pequeño de un solo módulo con nombre preciso, antes que alojar un módulo en un paquete al que no pertenece semánticamente.

    • Los paquetes pueden contener subpaquetes cuando existe una unidad lógica que lo justifica. La granularidad la dicta la semántica, no una regla de profundidad.

    • Las funciones, constantes y variables de un dominio llevan el prefijo del ente en mayúsculas: BD_nombre, WS_nombre. Los módulos usan el orden inverso: naturaleza_BD, naturaleza_WS. Esto agrupa visualmente por naturaleza en el árbol de archivos y por dominio en el código.

    • Los módulos de entorno, configuración y ajuste siguen esta nomenclatura fija:

    Nombre Propósito
    env ENVIRONMENT DIVISION — lo que el sistema conoce de sí mismo al arrancar
    setup Configuración interna sin intervención del usuario
    conf Configuración que requiere decisión del usuario

    Funciones¶

    • Nombres de funciones en minúsculas separadas por guión bajo _.

    • Esta regla de los guiones puede romperse usando capitalize, comenzando en minúscula, si el nombre produce "cacofonía visual".

    • Si no hay persistencia, función siempre.

    • Si varias funciones están interrelacionadas entre sí, usar clases.

    • Si un método tiene sentido separado de la clase, mejor no usar clases.

    • Ante la duda, usar clases.

    • Las funciones que se pasen como target a un Thread no serán lambdas — los tracebacks no las identifican. Se nombrarán así:

    • th_nombre — lanzadora de hilo a nivel de módulo.

    • ith_nombre — lanzadora de hilo interna a otra función o clase.

    • Si una función o un método tiene un solo consumidor, no se crea: su código va dentro de quien lo usa, como un bloque con su comentario. Se separa cuando aparece el segundo consumidor.

    • Funciones internas (definidas dentro de otra función o método, para ordenar el código de una sola pieza):

    • Nombre en minúsculas con guión bajo y empezando por _ (_elegir, _leer_toma), para que se vea a primera vista que son internas y no métodos.

    • Sin cierres (closures): no leen ni escriben variables locales de la función que las contiene, y nunca usan nonlocal. Una variable que viaja escondida de una función a otra no se ve al leer la línea que la usa. Solo pueden usar self y el alias de las constantes de la clase (kv = self.KV). El estado que compartan va como variable de instancia declarada (ver Clases) o como variable de clase, o se pasa como parámetro.

    • Una variable local no puede llamarse igual que una función interna ni que un parámetro: dentro de su ámbito, el nombre deja de ser la función y el error no avisa hasta que se ejecuta.

    Clases¶

    Denominaciones:

    • Nombre de las clases en capitalize comenzando en MAYÚSCULAS. Puede contener la palabra Class al final de su nombre para indicar visualmente que es una clase.

    • Nombre de los objetos instanciados de una clase, capitalize comenzando en minúsculas.

    • Las propiedades comenzarán por minúsculas, los métodos por mayúsculas y usarán un verbo en infinitivo.

    • Las propiedades booleanas empiezan con es (por ejemplo: objeto.esActivo).

    • Los métodos decorados como propiedades se nombrarán como si fuesen otras propiedades.

    • Los métodos de solo lectura comenzarán SIEMPRE con la palabra get.

    • Los métodos de solo escritura comenzarán SIEMPRE con la palabra set.

    • Si existe lectura y escritura para una propiedad, SIEMPRE se usará @property y setter con el mismo nombre, para que parezcan una propiedad y no dos métodos separados.

    Orden innegociable del código de la clase:

    • __slots__ será lo primero que aparecerá codificado en la clase, aunque esté vacío.

    • La excepción a esta norma se dará en las clases que van a soportar herencia múltiple. Para evitar el error multiple bases have instance lay-out conflict, dichas clases no tendrán __slots__, pero sí comentario que indique que esta es la razón por la cual no lo tienen.

    • Se podrán crear clases sin __slots__ cuando su herencia deba cambiar dinámicamente en tiempo de ejecución.

    • Si la clase hereda de otra que no usa __slots__ (por ejemplo, las ventanas de tkinter o customtkinter), su __slots__ no tiene efecto: la clase sigue teniendo __dict__ y admite cualquier atributo nuevo. Se mantiene __slots__ = [] por esta norma, con un comentario que diga que ahí no tiene efecto y por qué, y la protección se consigue con la declaración de todas las variables de instancia en el __init__ (ver más abajo).

    • Los literales mágicos serán lo segundo que se codificará, si es necesario.

    • __new__ será el tercer elemento codificado, cuando sea necesario.

    • __init__ será el cuarto elemento codificado.

    • Variables de instancia: todas se declaran en el __init__, justo después de super().__init__() y antes de cualquier lógica, en una sección propia # region Variables de instancia, cada una con su tipo y su comentario. Nunca se crea un self.algo nuevo en mitad de un método. Las que toman su valor más tarde (al crear un elemento, o en un método que las reinicia) llevan solo la anotación de tipo (self.ruta: ctk.StringVar); su valor inicial se escribe una sola vez, donde corresponda, y los métodos que las reinician solo asignan, no declaran.

    Principios de operatividad:

    • Las clases no deben permitir añadir propiedades en tiempo de ejecución, por esa razón utilizan siempre __slots__.

    • En caso de necesitar una clase que aumente sus propiedades en tiempo de ejecución, no se modificará una clase ya creada, sino que se creará una nueva clase que heredará las clases necesarias, pero no se modificará el comportamiento previsto de las clases definidas previamente.

    • La excepción a esta norma se aplicará cuando exista necesidad de aplicar técnicas como el monkey patching o el dynamic dispatch.

    Carpeta rec (recursos no Python)¶

    • Los recursos necesarios para la aplicación que no sean código Python (plantillas, imágenes, archivos de configuración, fuentes, CSS, JS, etc.) vivirán en una carpeta llamada rec (opcional _rec con guión bajo al frente).

    • El guión bajo la distingue visualmente del código y la sitúa primera en el orden alfabético, evitando que se confunda con un paquete.

    • rec no tendrá __init__.py ni ningún archivo .py. Si algo necesita código Python, no pertenece ahí.

    • Su ubicación sigue el mismo principio que hub:

    • <paquete>/rec/ → recursos exclusivos de ese paquete.

    • src/rec/ → recursos compartidos por más de un paquete.

    Ramas¶

    dev:        Rama/s en desarrollo.
PROTO:      Rama de prototipos (opcional: según cómo trabaje cada proyecto).
deploy:     Producto listo para el usuario final (aplicaciones).
Submodule:  Biblioteca lista para vendorizarse como submódulo (desarrolladores).
master:     Versión estable, nunca usar para desarrollo.

    Versiones¶

    • La versión del proyecto vive en un único fichero VERSION en la raíz del repositorio — una sola línea sin \r y única fuente de verdad.

    • src/main.py la lee al arrancar y la expone como __version__.

    • La ayuda (MkDocs) la muestra con 1.3 (ver Repo/doc/mkdocs/USO.md).

    • Remoto.sh la lee para el mensaje del commit de despliegue.

    • El versionado facilita la comprensión sin necesidad de conocimiento técnico:

    • Versión principal año y mes. Ejemplo: 26.05 (mayo del año 2026).

    • En caso de corrección de errores, aparecerá una letra pegada al mes de la versión que corrige. Ejemplo: 26.05b (segunda revisión de errores de la versión de mayo del 2026).

    • En caso de añadir mejoras en el mismo mes (altamente desaconsejado), se añadirá el día de la publicación. Ejemplo: 26.05.12.

    • En caso de correcciones sobre una versión de mejoras, letra pegada al día. Ejemplo: 26.05.12c (tercera revisión de errores de la versión de ese día).

    MUY IMPORTANTE - JAMÁS SE OFRECERÁ UNA VERSIÓN DE CORRECCIÓN CON APARIENCIA DE VERSIÓN DE MEJORAS.

    • JAMÁS LAS VERSIONES DE DESPLIEGUE SE SOBREPONDRÁN LAS UNAS A LAS OTRAS. SI APARECE UNA VERSIÓN DE MEJORAS, LAS CORRECCIONES SE HARÁN SIEMPRE SOBRE LA ÚLTIMA VERSIÓN DESPLEGADA REALMENTE, NO SOBRE LA VERSIÓN BASE.

    Flujo operativo¶

    Resultados del despliegue¶

    Proyecto para desarrollo:

    • Los mantenedores del proyecto utilizan la rama master como base.

    • Los usuarios de una biblioteca utilizan la rama Submodule como base.

    • La documentación generada con MkDocs (doc/Datasheet) se ofrece a los usuarios de la biblioteca. Puede eliminarse pero deberán gestionarse de manera personal los conflictos Git que esto origine.

    • Sólo el director del proyecto tiene permitido hacer push sobre la rama master.

    Aplicación para usuario final:

    • El arranque de la aplicación estará en el archivo ./main.sh.

    • Este script lo primero que realizará serán las verificaciones, copias previas y actualizaciones necesarias, desde el repositorio Git público.

    • El arranque de la aplicación será 100% transparente y sin pantalla de terminal alguna.

    Herramientas proporcionadas al mantenedor¶

    Viven en Repo y cada proyecto las usa a través de su enlace simbólico. Lo propio de cada proyecto va en su archivo de configuración, junto al enlace.

    H1 - Remoto.sh (Despliegue a un remoto público)¶

    • Copia una foto exacta de la rama de origen en la rama de destino y la sube a un remoto fuera de Gitea (GitHub, GitLab). Solo la usan los proyectos que se publican fuera.

    • Configuración propia: rec/scripts/remoto.conf (URL_REMOTO, REMOTO, RAMA_ORIGEN, RAMA_DESTINO, ARCHIVO_VERSION, ARCHIVO_REQUIREMENTS y REMOVE_PATHS, obligatoria aunque esté vacía).

    • Debe ejecutarse desde la rama de origen, sin cambios ni commit pendientes.

    Flujo:

    • Verifica el estado del repositorio, el remoto (lo crea si no existe) y los archivos necesarios.
    • Descarga la rama de destino, o la crea si no existe.
    • Copia la foto exacta de la rama de origen, sin merge.
    • Genera ARCHIVO_REQUIREMENTS en la raíz, si se pide.
    • Quita los enlaces BIB_REAL_slr: nunca se despliegan.
    • Convierte el resto de enlaces simbólicos en archivos reales.
    • Quita el bytecode versionado (.pyc, .pyo).
    • Quita REMOVE_PATHS.
    • Commit con la versión de VERSION y push al remoto.
    • Vuelve a la rama de origen y borra la rama de destino local.

    H2 - requirements.sh (Entorno y dependencias)¶

    • Configuración propia, obligatoria: rec/requirements/requirements.conf (RUTA_VENV, DESPLIEGUE, DESARROLLO y SISTEMA). Plantilla en Repo.

    • Suma las dependencias de cada biblioteca vendorizada, leídas de su propio requirements.conf a través de su BIB_REAL_slr. Si a alguna le falta, se para.

    • No genera archivos: pip lee las listas directamente de memoria.

    • Opciones: --mostrar, --deploy, --dev y --pip-despliegue (la usa Remoto.sh).

    H3 - mkgen.sh (Documentación MkDocs)¶

    • Genera la documentación del proyecto con el venv de Repo, a través de su enlace en la carpeta de MkDocs del proyecto.

    • serve muestra la documentación mientras se edita; al cortar con Ctrl+C genera el HTML final. build solo genera.

    • Las normas de uso están en Repo/doc/mkdocs/USO.md.

    H4 - bib.sh (Bibliotecas vendorizadas)¶

    • Sincroniza cada biblioteca de src/bib/ con su repositorio real, alcanzado a través de su enlace BIB_REAL_slr.

    • Copia src/ y los archivos de la raíz de la biblioteca; nunca toca nada más.

    • Trae cambios (Suite → Local), los lleva (Local → Suite) y detecta conflictos.

    H5 - SymlinksLocal.sh (Enlaces simbólicos)¶

    • Registro de los enlaces del proyecto en rec/scripts/sl/SymlinksLocal.txt.

    • Sufijos según el destino: _slp dentro del propio repo, _slr dentro de $HOME/Dev, _sla fuera.

    • Opciones: --leer (actualiza el registro), --montar (recrea los enlaces), --verificar (solo lectura) y --deducir (corrige sufijo y destino).

    H6 - Generar_UE.sh y Reponer_REPO.sh (Proyectos nuevos)¶

    • Generar_UE.sh (solo en Repo) genera __UsarEste, la base para crear un proyecto nuevo: copia los archivos de Repo y crea enlaces para los que tienen hermano _sl. Lo que está en SOLO_REPO nunca pasa.

    • Reponer_REPO.sh crea en un proyecto existente los enlaces _sl que tenga Repo: tras clonar un proyecto limpio o al migrar uno antiguo.

    Un poco de los 80¶

    En los años 80, antes de las bases de datos relacionales tipo SQL, los programadores gestionaban ficheros físicos directamente en su código. No existían gestores que protegieran los nombres de los campos ni herramientas de refactorización.

    El mayor peligro era la invisibilidad: no saber si una variable era un dato temporal de memoria o un campo real que se persistía en disco. Cambiar un nombre implicaba buscar a mano en cientos de ficheros de texto (Git ni siquiera se había pensado).

    Para resolverlo se adoptó una convención de prefijos que permitía identificar la naturaleza del dato con solo mirar la variable:

    • K para las claves.
    • D para los datos.

    Gracias a los objetos, la confusión entre memoria y disco desaparece, pero dentro del objeto ocurre el mismo problema: invisibilidad de código y cambios de nombre obligan a revisar toda la clase.

    Se recupera esa visibilidad dentro de los objetos con la misma convención. El ejemplo histórico:

    # --- Objeto cámara
class Camara(object):

    # --- Registro de la cámara en la BD

    # --- Claves o Keys
    __K01 = "A_nombre"      # --- Nombre de la cámara
    __K02 = "B_num"         # --- Número de serie de la cámara

    # --- Datos
    __D01 = "A_pausa"       # --- La cámara entra en pausa
    __D02 = "B_descrip"     # --- Descripción de la cámara
    __D03 = "C_shutterlag"  # --- Milisegundos de shutterlag

    Este patrón define un conjunto de literales mágicos controlados: cada campo real de la base de datos se representa mediante un alias interno (__K01, __D01, etc.).

    Gracias a esta capa de indirección, si el nombre del campo cambia en la base de datos, solo es necesario modificar la constante correspondiente, sin alterar el resto de la clase.

    Las claves y datos se declaran como propiedades de clase privadas, utilizando el enmarañado de nombres descrito en PEP8 (double underscore). Dentro de los métodos, su acceso siempre requiere el prefijo self.

    Cada clave del diccionario tiene un significado fijo. Los marcadores especiales son:

    • Clave ausente — no genera ese argumento en el Field.
    • "~" — genera una propiedad o método dinámico (fieldname_rol) que el programador implementa.
    • Cualquier otro valor — se linkea con su clave en el diccionario.

    El generador dclgen lee el bloque _d* y produce automáticamente:

    1. El bloque de atributos (if True:): getter/setter por campo, con sus propiedades dinámicas y método fieldname_validators pegados al campo.
    2. El bloque REG: reproducción del bloque _d* de referencia.
    3. El __init__ con MontarPROTO completo, protegido con if not (self.PROTO):, y el Field de KEY siempre como primer campo.

    Las funciones de tipo combo devuelven siempre tuple, no list, porque sus opciones son datos fijos que no deben modificarse en tiempo de ejecución.
